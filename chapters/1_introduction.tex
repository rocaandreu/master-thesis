\section{Context and motivation}

Any computer connected to a network contains some sort of network interface, usually in the form 
of a \gls{nic} which acts as an interface between the physical layer (e.g. Ethernet or Wi-Fi), 
and the rest of the system. \\

% As network speeds increased and more advanced features were employed in network processing, general purpose CPUs could not always 
% keep up with all the packet processing at the required rate and volume. In modern high-speed applications, many network processing tasks are 
% therefore offloaded to the \gls{nic}. 
As network speeds increased and more advanced features were employed in network processing, the amount of CPU computation 
available per packet decreased, making CPU-based packet processing increasingly expensive and motivating offloading 
part of the processing to programmable NICs/SmartNICs \cite{wang2022fpgAnic} \cite{kim2023iotcp}.\\

A SmartNIC contains specific hardware that can perform tasks such as packet classification, filtering, flow handling, 
and FEC processing directly on the network interface. This specialized hardware provides a much higher efficiency and speed,
which allows packets to be processed at or near line rate while freeing the CPU to focus on application-level computation.

\subsection{Forward Error Correction over Groups of Packets}
\label{subsec:fec-generations}

Forward Error Correction (\gls{fec}, and also called channel coding) is a type of digital signal processing that improves data reliability 
by introducing a known structure into a data sequence prior to transmission or storage. This structure enables a receiving system 
to correct errors caused by corruption or packet erasures from the channel and the receiver. As the name implies, this coding technique 
enables the decoder to correct errors without requesting retransmission of the original information. However, this approach requires 
additional processing and bandwidth on the communication channel.\\

The HyperNIC project focuses particularly on correcting packet erasuers, and in this context \gls{fec} is often applied across multiple packets. 
By encoding packets together, the sender can generate repair packets that allow the receiver to reconstruct one or more packets lost during 
transmission, rather than adding independent redundancy to every packet. This makes the available redundancy more efficient and can reduce 
the need for retransmissions, which is particularly valuable in unreliable, multicast, or high-loss networks. The trade-off is that larger FEC 
blocks generally require more buffering and can introduce additional decoding latency, since the receiver may need to collect enough packets 
from the block before recovery is possible. Standards such as the IETF's FEC framework and Raptor FEC scheme explicitly organize data into 
source blocks for this purpose \cite{watson2011fec}.\\

Needless to say, the packets across which the encoding is performed must have the same destination, otherwise the additional information 
would be pointless. Because of this, network processors must detect packet flows and perform the encoding accordingly. It is important to remark 
that these FEC computations are performed over groups of a fixed amount of packets, and that the size of the group is known as the 
generation size.

\subsection{HyperNIC project}
This project is done as a part of the HyperNIC project, an initiative funded by the Deutsche Forschungsgemeinschaft (DFG, German Research Foundation), the central self-governing 
research funding organisation in Germany. The project investigates how SmartNICs can improve the resilience and reliability of time-sensitive 
communication in connected cyber-physical systems. By combining hardware acceleration with techniques such as network coding and fault-tolerant communication, 
HyperNIC aims to enable reliable, low-latency data exchange in the presence of network failures or disruptions, while reducing the processing load on host CPUs.

The problem to solve is simple at a surface level as illustrated in the diagram \ref{fig:problem_definition},

belonging to a single flow. As stated previously, FEC calculations must be performed on a per-flow basis and over generation-sized blocks; therefore 
a mechanism is needed to collect and separate packets by flow, accumulate complete generations, and feed them to the FEC encoder in the 
required order and block size.

\section{Methodology}
The development of this module followed an iterative design methodology, in which the architecture was progressively refined through repeated 
cycles of design, implementation, and evaluation. Initially, different architectural approaches were investigated to determine how packets could 
be efficiently organized and buffered before being processed by the FEC encoder. Multiple approaches have been implemented and evaluated through 
functional simulation to verify its correctness and through synthesis to assess its hardware resource utilization, timing, and overall 
feasibility for the target platform.\\

Particular attention was given to the HBM management architecture, for which several approaches were 
explored to improve memory utilization, access efficiency, and scalability. The results obtained from each iteration informed subsequent 
design decisions, leading to modifications of the buffering, queueing, and memory-management mechanisms. The architecture presented in this 
thesis therefore represents the final iteration of this iterative development process, selected based on the functional and hardware-level 
evaluations performed throughout the design. \\

The proposed design is evaluated in simulation using a UVM-like testbench with configurable stimulus patterns with the aim of analysing its 
performance under different scenarios, and synthesized in an out-of-context flow to assess FPGA resource usage.

\section{Scope and limitations}
%This is just a first iteration... No RX side...

The packet buffer presented in this thesis aims to provide a versatile platform to evaluate different FEC strategies and schemes on a 
real network environment. \\

Further development could be done to integrate it into a complete FPGA-based system. In particular, the 
current implementation could be extended with more scalable packet queue implementation, dynamically configurable FEC generation sizes, and 
mechanisms for handling different flow priorities. These aspects are outside the scope of the current implementation, but the implemented 
design intentionally facilitates these future modifications. \\

The scope of this thesis targets the transmit (TX) side of the packet buffer architecture, so the corresponding receive (RX) 
side is therefore not implemented or evaluated as part of this work. Nevertheless, its design could follow a similar architectural approach 
to the TX side, allowing a significant portion of the existing design, including the buffering and memory-management mechanisms, to be reused. 
Consequently, the implementation presented here provides a foundation for extending the packet buffer architecture towards a complete TX/RX 
system in future work.

\section{Report structure}

The thesis is structured as follows:

\begin{enumerate}
  \item \textbf{Introduction}: Introduces the context and motivation of the work, defines the research objectives, and provides an overview of the main concepts, challenges, and methodology.
  \item \textbf{Background}: Presents the technical foundations relevant to the work, particularly regarding the shared memory architecture.
  \item \textbf{Design}: Defines the system requirements and presents the architecture of the packet buffer.
  \item \textbf{Implementation}: Describes in further depth the implementation of the hardware modules and control logic.
  \item \textbf{Evaluation}: Details the verification and testing procedures performed in simulation and presents the resulting performance measurements and resource utilization.
  \item \textbf{Discussion}: Discusses and interprets the obtained results, addressing the main issues encountered during development as well as identified bottlenecks, possible improvements, and future directions.
  \item \textbf{Conclusion}: Summarizes the main findings of the work, discusses its limitations, and presents concluding remarks and possible directions for future work.
\end{enumerate}
